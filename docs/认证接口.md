# 用户认证接口

本文描述新版 `relayim` 用户认证链路。旧 `/users` 路由已从主 Router 下线，源文件仅作为迁移参考保留，不参与运行时接口注册。

注册、登录、刷新和 WebSocket Ticket 均受 Redis 滑动窗口限流保护。通用状态码、响应头和策略配置见 [接口限流](./接口限流.md)。

## 1. 注册

```http
POST /api/v1/auth/register
Content-Type: application/json
```

请求：

```json
{
  "username": "alice",
  "password": "password123",
  "confirm_password": "password123",
  "nickname": "Alice"
}
```

成功响应：

```http
201 Created
```

```json
{
  "id": "1839281749283749120",
  "username": "alice",
  "nickname": "Alice",
  "avatar_url": "",
  "bio": ""
}
```

规则：

- 用户名长度为 2 到 32 个 Unicode 字符。
- 用户名只允许字母、数字、下划线和中划线。
- 密码长度为 8 到 72 字节，上限来自 bcrypt。
- 同一个事务创建 `users` 和 `user_profiles`。
- 用户名重复返回 `409 Conflict`。

## 2. 登录

```http
POST /api/v1/auth/login
Content-Type: application/json
```

请求：

```json
{
  "username": "alice",
  "password": "password123"
}
```

成功响应：

```json
{
  "token": "<JWT>",
  "refresh_token": "rt_<随机字符串>",
  "refresh_expires_at": "2026-12-08T08:00:00Z",
  "device_id": "1839281749283749123",
  "user": {
    "id": "1839281749283749120",
    "username": "alice",
    "nickname": "Alice",
    "avatar_url": "",
    "bio": ""
  }
}
```

规则：

- 用户名不存在和密码错误统一返回 `401 Unauthorized`，防止账号枚举。
- 禁用账号返回 `403 Forbidden`。
- JWT 中的 `user_id` 和 `sub` 都使用 Snowflake 字符串。
- JWT 同时写入 Redis 白名单，键为 `token:<JWT>`。
- Refresh Token 只返回原始值，MySQL 仅保存 SHA-256 摘要。
- 客户端可传回上次的 `device_id`、`device_name` 和 `platform`；不传时创建新的 Web 设备。

## 3. 刷新 Access Token

```http
POST /api/v1/auth/refresh
Content-Type: application/json
```

```json
{
  "refresh_token": "rt_<随机字符串>"
}
```

服务端锁定当前 Refresh Token 行，确认未过期、未撤销且设备有效后：

1. 立即撤销旧 Refresh Token。
2. 生成新 Refresh Token 并保存新摘要。
3. 签发新的 Access Token。

```json
{
  "token": "<新 JWT>",
  "refresh_token": "rt_<新随机字符串>",
  "refresh_expires_at": "2026-12-08T08:00:00Z"
}
```

旧 Refresh Token 重放返回 `401 Unauthorized`。客户端必须原子替换本地 Access Token 和 Refresh Token。

## 4. 退出登录

```http
POST /api/v1/auth/logout
Authorization: Bearer <JWT>
Content-Type: application/json
```

```json
{
  "refresh_token": "rt_<随机字符串>"
}
```

成功后返回 `204 No Content`，同时撤销当前 Access Token 和提交的 Refresh Token。客户端随后清除本地凭证。

## 5. 当前用户

```http
GET /api/v1/me
Authorization: Bearer <JWT>
```

成功响应：

```json
{
  "id": "1839281749283749120",
  "username": "alice",
  "nickname": "Alice"
}
```

中间件会依次校验：

1. Authorization Header。
2. JWT 签名、算法和过期时间。
3. `sub` 与 `user_id` 是否一致。
4. Redis 黑名单。
5. Redis Token 白名单。

### 查看指定用户公开资料

```http
GET /api/v1/users/:user_id
Authorization: Bearer <JWT>
```

返回昵称、头像和个人简介等公开字段，不返回密码哈希、账号状态、设备或内部基础设施信息。前端用于好友头像和用户搜索结果的资料弹窗。

### 修改当前用户资料

```http
PUT /api/v1/me
Authorization: Bearer <JWT>
Content-Type: application/json
```

```json
{
  "nickname": "新的昵称",
  "bio": "正在完善 RelayIM"
}
```

- 昵称去除首尾空格后不能为空，最多 64 个 Unicode 字符。
- 简介最多 500 个 Unicode 字符；空字符串表示清除简介。
- 更新只修改当前认证用户，请求体不能指定其他用户 ID。
- 成功后返回与 `GET /api/v1/me` 相同的资料结构。

### 上传头像

```http
POST /api/v1/me/avatar
Authorization: Bearer <JWT>
Content-Type: multipart/form-data
```

表单字段为 `file`。支持 JPEG、PNG、WebP 和 GIF，单张最大 5 MB。服务端会读取文件头识别真实类型，不信任文件名或客户端 MIME。

上传成功后返回当前用户资料，其中 `avatar_url` 是稳定地址：

```text
/api/v1/users/1839281749283749120/avatar?v=1770000000000
```

头像对象保存在 S3 兼容对象存储中，浏览器通过公开只读接口加载；地址中的版本参数用于替换头像后刷新缓存。

### 移除头像

```http
DELETE /api/v1/me/avatar
Authorization: Bearer <JWT>
```

成功后清空头像对象键和展示地址，并尽力删除旧对象。

## 6. 本地启动与测试

从项目根目录启动：

```powershell
.\scripts\run-server.ps1
```

PowerShell 示例：

```powershell
$body = @{
    username = "alice"
    password = "password123"
    confirm_password = "password123"
    nickname = "Alice"
} | ConvertTo-Json

$user = Invoke-RestMethod `
    -Method Post `
    -Uri "http://127.0.0.1:8081/api/v1/auth/register" `
    -ContentType "application/json" `
    -Body $body

$loginBody = @{
    username = "alice"
    password = "password123"
} | ConvertTo-Json

$login = Invoke-RestMethod `
    -Method Post `
    -Uri "http://127.0.0.1:8081/api/v1/auth/login" `
    -ContentType "application/json" `
    -Body $loginBody

$headers = @{
    Authorization = "Bearer $($login.token)"
}

Invoke-RestMethod `
    -Method Get `
    -Uri "http://127.0.0.1:8081/api/v1/me" `
    -Headers $headers
```

## 7. 代码位置

| 文件 | 职责 |
| --- | --- |
| `internal/identity/model.go` | 用户和资料持久化模型 |
| `internal/identity/repository.go` | 注册事务、唯一键冲突和查询 |
| `internal/identity/service.go` | 输入校验、密码、资料修改和业务错误 |
| `internal/platform/authn/manager.go` | JWT 签发、统一校验、Redis 白名单与撤销 |
| `internal/middleware/auth.go` | 把认证结果注入 HTTP 请求上下文 |
| `internal/identity/handler.go` | HTTP 参数和错误映射 |
| `internal/router/identity/identity_router.go` | 路由组装 |

## 8. 统一认证组件

`internal/platform/authn.Manager` 是 HTTP、WebSocket 和新旧登录入口共用的认证边界：

- `IssueToken`：生成 JWT，并写入 Redis 白名单。
- `Authenticate`：校验 JWT、黑名单和白名单，返回统一的 `Session`。
- `IssueWSTicket`：生成 30 秒、单次使用的 WebSocket Ticket。
- `IssueRefreshToken`：生成 Refresh Token 和 SHA-256 摘要。
- `ConsumeWSTicket`：使用 Redis `GETDEL` 原子消费 Ticket。
- `Revoke`：删除白名单并写入黑名单，使当前 Token 立即失效。

HTTP 通过 `AuthMiddleware` 调用 `Authenticate`，再把 `Session.UserID` 注入请求上下文；WebSocket 建连前通过 `ConsumeWSTicket` 换取用户 ID。业务 Handler 不重复解析 JWT，也不直接操作 Redis。

## 9. WebSocket Ticket

WebSocket 不再直接使用长期 Access Token。登录用户先通过受保护接口获取一次性票据：

```http
POST /api/v1/auth/ws-ticket
Authorization: Bearer <JWT>
Content-Type: application/json
```

首次连接可以创建设备：

```json
{
  "device_name": "Chrome",
  "platform": 1
}
```

客户端应保存响应中的 `device_id`，后续申请 Ticket 时传回：

```json
{
  "device_id": "1839281749283749120"
}
```

```json
{
  "ticket": "短时随机票据",
  "expires_in_seconds": 30,
  "device_id": "1839281749283749120",
  "device_name": "Chrome",
  "platform": 1
}
```

服务端只在 Redis 中保存票据 SHA-256 摘要，并在消费时使用 `GETDEL` 原子删除。Ticket 有效期 30 秒且只能建立一次 WebSocket 连接。Ticket 同时绑定 `user_id + device_id`。

### Ticket 限流

Ticket 接口在认证之后、创建设备之前执行 Redis ZSET 原子滑动窗口限流。默认策略：

- 单用户最近 1000 ms 内最多 10 次。
- 全实例最近 1000 ms 内最多 250 次。
- 只把放行请求写入窗口，被拒绝请求不会继续放大计数。

超过限制返回：

```http
429 Too Many Requests
Retry-After: 1
X-RateLimit-Scope: user
```

```json
{
  "error": "请求过于频繁，请稍后重试"
}
```

客户端应读取 `Retry-After` 并加入少量随机抖动后重试，不能立即形成重试风暴。限流键带 TTL，Redis 不可用时返回 `503`，不会绕过限流。
