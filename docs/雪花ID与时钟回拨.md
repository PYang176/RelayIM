# 雪花 ID 与时钟回拨

项目使用 41 位毫秒时间戳、10 位 Worker ID 和 12 位毫秒序列号生成 Snowflake ID。当前方案不引入独立发号服务，只使用 Go 单调时钟和数据库启动水位处理时钟回拨。

## 1. 进程运行期间

`bwmarrin/snowflake` 的生成基准保留了 Go 单调时钟。NTP/chrony 对系统墙钟的小幅调整在正常情况下不会让序列时间倒退，因此进程运行期间的短时校时由单调时钟兜底。

同一 Worker 的生成操作仍由互斥锁保护；同一毫秒序列耗尽时等待下一毫秒，不并发生成重复序列。

## 2. 应用启动时

单调时钟在进程重启后会重新计算，单靠底层库无法发现系统墙钟是否已经落后于历史 ID。应用在初始化雪花节点前执行：

1. 查询用户、设备、好友、会话、消息、附件和事件等表的 `MAX(Snowflake ID)`。
2. 从最大 ID 中提取最后一次生成时间。
3. 当前墙钟落后不超过 5 秒时，等待墙钟追平后继续启动。
4. 当前墙钟落后超过 5 秒时，拒绝启动并输出需要校准时间的错误。

这一步不新增数据库表、不启动后台协程，也不要求每次发号访问数据库。

如果数据库中没有历史 ID，则跳过启动水位检查。

## 3. Worker ID

每个运行实例仍必须使用不同的 Worker ID：

```text
GINCHAT_SNOWFLAKE_WORK_ID
```

数据库启动水位只能防止时间回拨造成的重复，不能解决两个实例配置同一个 Worker ID 的问题。

## 4. 故障处理

遇到“系统时钟落后数据库雪花时间水位”的启动错误时：

1. 检查 Windows、Linux 或虚拟机宿主机的当前时间。
2. 启用并检查 NTP/chrony 同步状态。
3. 修正时间后重新启动应用。
4. 不要在已知墙钟落后的机器上反复强制启动。

该策略优先保证不生成重复主键，而不是在时间异常时继续提供发号服务。
