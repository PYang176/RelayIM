# WebSocket 空闲连接阶梯报告

## 1. 测试日期

2026-11-08

## 2. 测试目标

逐级验证单实例 RelayIM 在 100、500、1,000、2,000、5,000 个空闲 WebSocket 连接下的：

- 一次性 Ticket 建连成功率。
- WebSocket 握手延迟。
- 20 秒连接稳定性。
- 服务端连接数、Goroutine 和堆内存。
- 连接关闭后的资源回收。

## 3. 测试环境

| 项目 | 配置 |
| --- | --- |
| CPU | AMD Ryzen 7 5800H，8 核 16 线程 |
| 内存 | 32 GB |
| 操作系统 | Windows 11 家庭版，10.0.26200 |
| Go 服务 | Windows 本机直接运行 |
| Redis | Docker Desktop WSL2，Redis 7.4 |
| 压测工具 | Docker 容器 `grafana/k6:0.57.0` |

其他业务基础设施保持运行，但本场景只建立 WebSocket 连接，不发送聊天消息。

## 4. 测试方法

- 服务限制每个用户最多 10 个连接。
- 100、500、1,000 个连接分别使用 10、50、100 个独立用户。
- 100 至 2,000 档使用 0 至 5 秒随机建连爬坡，每连接保持 20 秒；由于保持时间显著长于爬坡时间，全部连接存在完整重叠区间。
- 5,000 档使用 `ramping-vus`，45 秒逐步增加至 5,000，所有连接保持到统一结束时间，确保至少 20 秒的完整重叠。
- k6 自动完成 WebSocket Ping/Pong 协议处理。
- 测试期间每秒请求一次 `/metrics`，记录服务端连接、Goroutine 和堆内存峰值。

## 5. 结果汇总

| 连接数 | 建连成功 | 握手 P95 | 握手 P99 | 最大握手 | 服务端连接峰值 | Goroutine 峰值 | 堆内存峰值 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 100 | 100 / 100 | 11.17 ms | 17.54 ms | 23.56 ms | 100 | 未完整采样 | 未完整采样 |
| 500 | 500 / 500 | 4.81 ms | 8.56 ms | 21.35 ms | 500 | 1,543 | 28.1 MiB |
| 1,000 | 1,000 / 1,000 | 21.83 ms | 52.91 ms | 75.07 ms | 1,000 | 3,043 | 45.6 MiB |
| 2,000 | 2,000 / 2,000 | 8.73 ms | 39.02 ms | 72.25 ms | 2,000 | 6,043 | 82.2 MiB |
| 5,000 | 5,012 / 5,017 | 6.22 ms | 20.90 ms | 1,104 ms | 5,000 | 15,069 | 191.8 MiB |

共同结果：

- 100 至 2,000 档建连成功率均为 100%。
- 5,000 档完成 5,017 次连接尝试，其中 5,012 次成功，成功率 99.90%，高于 99% 阈值。
- 5,000 档服务端采样确认同时在线的目标连接数达到 5,000，并保持至少 20 秒。
- 20 秒保持期间未记录异常关闭。
- 连接成功关闭后，服务端 `relayim_websocket_connections` 回到 0。
- 所有连接均满足每用户最多 10 连接的现有约束。

## 6. 观察

### 6.1 连接建立

2,000 连接时握手 P95 为 8.7 ms。5,000 连接采用协调爬坡后，P95 为 6.2 ms、P99 为 20.9 ms，说明均匀建连可以避免瞬时认证和 TCP 建连洪峰。

### 6.2 Goroutine

500 连接时 Goroutine 峰值约 1,543，1,000 连接约 3,043，2,000 连接约 6,043，5,000 连接约 15,069。增量与连接数近似线性，符合当前连接读协程、写协程和运行时代码路径的预期。

### 6.3 内存

500 连接时堆内存采样峰值约 28.1 MiB，1,000 连接约 45.6 MiB，2,000 连接约 82.2 MiB，5,000 连接约 191.8 MiB。

5,000 连接时 Go 进程 RSS 峰值约 405.7 MiB，打开文件描述符峰值 10,661。该数据包含连接缓冲、Redis 心跳、Ticket 验证和 GC 时序影响，不能直接当成单连接固定成本。

### 6.4 资源回收

测试结束后连接数回到 0。服务端随后 Goroutine 回落到约 41，说明正常关闭路径可以释放连接相关协程。

## 7. 与目标的关系

需求目标是 5,000 个空闲 WebSocket 连接。本轮已经验证 5,000 个连接同时在线并保持 20 秒，但连接尝试成功率为 99.90%，仍需通过更长保持时间和多轮重复测试确认稳定性。

下一步应继续执行 2,000 和 5,000 连接阶梯，同时记录：

- Windows 文件描述符和端口占用。
- Go 进程 RSS，而不只是堆内存。
- CPU、GC 暂停和调度延迟。
- 客户端 k6 自身资源占用，避免压测机先成为瓶颈。
- 连接稳定保持 5 至 10 分钟后的 Ping/Pong 和资源变化。

## 8. 已知限制

- 5,000 档在完整重叠区间保持 20 秒，短于服务端 25 秒 Ping 周期。
- 未覆盖网络抖动、丢包和断线重连。
- k6 客户端与服务端运行在同一台电脑。
- 未发送业务消息，不包含群扇出和回执写入。
- 5,000 档有少量额外会话和 5 次连接级失败，需要继续排查是否是 k6/Windows 瞬时端口压力。

## 10. 测试方法修正

第一版 5,000 测试在数秒内集中申请 Ticket，出现大量 HTTP 500 和短暂连接拒绝；第二版虽然所有会话最终建立，但随机建连加固定保持时间只形成约 40% 的同时在线重叠，不能证明 5,000 连接容量。

最终版本改为协调式 `ramping-vus`：

- 45 秒建立至 5,000 VU。
- 所有已建立连接保持到统一结束时间。
- 服务端采样确认 `relayim_websocket_connections` 达到 5,000。
- 前两版不满足容量口径，不作为通过结果。
