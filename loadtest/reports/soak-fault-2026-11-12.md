## 4. 短时并发容量

场景使用 40 个独立发送账号、40 个 VU，每账号每秒发送 1 条消息，持续 2 分钟。

| 指标 | 结果 |
| --- | ---: |
| 并发发送账号 | 40 |
| 完成消息 | 4,680 |
| 业务检查 | 9,360 / 9,360 |
| 吞吐 | 39.00 条/秒 |
| 平均延迟 | 25.58 ms |
| P95 | 46.80 ms |
| P99 | 61.82 ms |
| 最大延迟 | 82.42 ms |

消息全局限流配置为每 10 秒 500 条，即平均 50 条/秒。本次验证到 40 个并发发送会话和约 39 条/秒，未达到系统资源上限，主要受测试发送频率和全局限流约束。

当前可对外表述：

- 已验证 20 个消息发送会话持续稳定运行 30 分钟。
- 已验证 40 个消息发送会话短时并发运行 2 分钟，吞吐约 39 条/秒。
- 空闲 WebSocket 连接另有 5,000 连接验证报告。

不能将这三个数字直接合并表述为“5,000 个活跃发送用户”。

## 5. 基础设施故障注入

### 5.1 RabbitMQ

- RabbitMQ 停止期间发送 3 条消息，接口均返回 `201` 并写入 Outbox。
- Outbox pending 峰值 3。
- RabbitMQ 恢复约 12.42 秒后，主消费队列为 0，消费者数量为 1。
- 中断期间 3 条消息均可从历史接口读取。
- 重试队列为 0，DLQ 在测试前后均为 21，没有新增死信。

DLQ 中的 21 条消息是测试前已经存在的历史残留，本次未清理或重放。正式部署前应单独检查来源。

### 5.2 Redis

- Redis 停止期间，认证、消息发送和 `/health/ready` 均返回 `503`。
- Redis 恢复约 11.45 秒后可以重新登录并发送消息，消息接口返回 `201`。
- 本轮为 Redis 客户端增加了连接、读取、写入和连接池超时，并为 HTTP 认证增加 5 秒总超时。

### 5.3 MySQL

- MySQL 停止期间，消息发送返回 `500`，`/health/ready` 返回 `503`。
- MySQL 恢复约 11.36 秒后消息发送恢复为 `201`。
- 连接池在数据库恢复后可以重新建立连接。

原始摘要：[fault-injection-2026-11-12.json](./fault-injection-2026-11-12.json)

## 6. 已知限制

- 长稳场景只验证 HTTP 写入、Outbox 和 RabbitMQ 消费，不包含 5,000 个活跃 WebSocket 同时收发消息。
- 40 VU 是已验证并发发送会话，不是系统理论最大值。
- 故障注入为单实例、单节点本地环境，未覆盖网络分区和磁盘故障。
- 结果来自同机 Docker 环境，不能直接当作多机生产集群容量。
